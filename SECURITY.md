# Security

RunClub runs GitHub Actions jobs on your own Windows machine. A job is code from a repository, and that code runs on
your computer. This page says whom RunClub trusts, what a job can and cannot reach, and which risks are accepted on
purpose.

## Reporting a vulnerability

Please use GitHub's **private vulnerability reporting** for this repository (Security tab → "Report a vulnerability").
Do not open a public issue for a security problem. There is no e-mail address for reports.

## Trust model

**Code in a repository with a pool is trusted code.** RunClub isolates jobs from each other and from the machine as far
as Docker allows, but this is not a boundary against every attack: a bug in the Linux kernel or in Docker can reach
further. Only add a pool for repositories whose code you would also run by hand. That includes workflows that check
out code from a pull request on purpose (`pull_request_target`, `issue_comment`, `workflow_run`): RunClub does not
look into workflows, so such code runs on your machine like any other.

RunClub enforces this where GitHub lets it check:

- **Private repositories only.** A pool cannot be added for a public repository. If a repository with a pool becomes
  public, its pool is paused, its jobs are routed back to GitHub's runners, and it cannot be resumed until the
  repository is private again.
- **No pull requests from forks in organizations.** In a private repository on a personal account, only people with
  write access can fork it, so their pull requests are already trusted. In an organization, members with read access
  can fork. If an organization repository allows workflows from fork pull requests ("Fork pull request workflows in
  private repositories" → "Run workflows from fork pull requests"), its pool is not added or is paused, **even if
  approval is required**. If RunClub cannot read that setting, the repository counts as exposed. Once a check
  finds the setting off, the pool can be resumed by hand.
- **When it checks.** When a pool is added, when RunClub starts, and every 10 minutes. A pool takes jobs only while
  the last successful check is less than 25 minutes old: after a start it waits for the first one, and if checks keep
  failing (no network, GitHub's rate limit used up), RunClub retries every minute and the pool rests once the last
  successful check is 25 minutes old. **Between two checks there is a window of up to 10 minutes** (up to 25 minutes
  while checks fail) in which a job can start on a repository that has just become public or started allowing fork
  pull requests.
- **A job that is already running finishes** when a repository is found public or allowing fork pull requests. Its
  pool takes no further jobs.

## What a job can reach

Every job gets a fresh pair of containers that is removed afterwards with its volumes: the runner container and its own
Docker daemon.

- **Docker daemons without privileges.** No container runs with `--privileged`. The job's Docker daemon and the
  per-repository build service (BuildKit) run as ordinary users in their own user namespaces (rootless). A job that
  breaks out of a container it started lands in its daemon's container as an unprivileged user, not in the Docker VM.
  Inside its own daemon a job can still start containers with `--privileged` and use user namespaces; this exposes
  more of the kernel than a plain container does, so a kernel bug there is the most likely way to `root` in the VM.
- **Seccomp profile.** These daemons run with Docker's default seccomp profile plus only the system calls they need for
  their namespaces (`linux/seccomp.json`, generated by `scripts/seccomp.js`; `keyctl` only for the session keyring
  that runc creates). There is no fallback to `unconfined`: if a daemon does not start with the profile, no runner is
  started for that pool and RunClub's log says why.
- **The runner container** has `root` via `sudo` for the job's steps, with Docker's default capabilities minus a few no
  job needs. Breaking out of it means `root` in the Docker VM. This is why the trust model above matters.
- **No host Docker socket, no Windows folders.** Neither is mounted into any job container.
- **One network per pair.** Jobs do not share a Docker network with each other. The build service of a repository has
  its own network and is reachable only through a socket that is mounted read-only into that repository's jobs.
- **One-time runner registration.** Each runner is registered for exactly one job (just-in-time configuration).
- **The local service** (the app's dashboard on `127.0.0.1`) answers only with the key of the running program. The
  app window receives it at start; it is also stored in RunClub's data folder (`%APPDATA%\RunClub\data\access.key`),
  which no job can reach. Requests that change something also need a token from the page. A job can reach `127.0.0.1`
  of Windows through `host.docker.internal`, but without the key it only learns that RunClub is running (`/api/ping`
  and the fonts answer without it). Pages carry a strict Content Security Policy.
- **Updates** are signed; see “Updates” below. Installers are not code-signed (Authenticode) yet.

## Updates

RunClub updates itself from this repository's GitHub releases (`src/updater.js`, `src/signature.js`).

- **What is signed.** Every release carries a small manifest, `runclub-update.json` (repository, version, channel,
  installer name, size, SHA-512, commit, time), and its Ed25519 signature, `runclub-update.json.sig`. The signature
  covers a fixed prefix plus the manifest's exact bytes.
- **Who signs.** Only the maintainer, on their own computer (`npm run release`), with a passphrase-encrypted private
  key. The key is never in CI, in a GitHub secret or in the repository; no workflow publishes releases. So a stolen
  GitHub token, a rogue workflow with `contents: write` or a compromised account can create a release, but not one
  the app accepts. One way remains: a commit on `main` that swaps a public key in `src/signature.js`, which the
  maintainer would then sign along. `npm run release` therefore stops when the keys differ from those of the last
  release and shows both, unless `--keys-changed` says the change is intended.
- **What the app checks, in this order:** manifest and signature are present (otherwise nothing is downloaded, and
  there is no fallback to electron-builder's `latest.yml`); the signature holds for one of the two public keys built
  into the app, before the manifest is even parsed; the manifest names this repository and exactly the release's
  version, that version is newer than the running one (no downgrade, no replay of an old signed release under a new
  tag), and a beta never reaches the Stable channel; the download stops beyond the signed size or after a minute
  without data; the installer's SHA-512 matches the manifest. Manifest and signature are read up to 64 KB. Right
  before the installer starts, its size and SHA-512 are checked once more; checks stop while an update installs.
- **A refused release doesn't block.** If the newest release fails these checks (or lacks its installer), the app
  logs it once and tries the next older ones, up to five. So someone who can create releases cannot stop all updates
  with an unsigned `v99.0.0`, including the one that replaces a stolen key; only more than five such releases would.
- **Two keys.** The app carries the public keys of a primary key (signs every release) and of a backup key (kept
  offline). Either one is accepted.
  - *Primary key lost:* the backup key signs the next release; that release carries a new primary public key next to
    the backup. Installations notice nothing.
  - *Primary key stolen:* the same, and the stolen key is removed in that release. Limit: until an installation has
    updated to it, the thief can still ship an update to it and may be faster. Every scheme with built-in keys has
    this window.
  - *Both lost:* installations can no longer update themselves; users have to install the new version by hand.
- **Limits.** If the maintainer's computer is compromised while the key is unlocked, the key is gone; the passphrase
  protects a stolen copy of the file, not a live attack, and only as well as it is strong: the file is encrypted with
  PBKDF2 at OpenSSL's default rounds, so `scripts/keygen.js` asks for at least 20 characters (several words). The
  key is only opened after the build, so it is not in memory while electron-builder runs. Hiding new releases (an
  attacker who withholds updates, or floods the list with refused ones) is not detected. Versions up to 0.1.0-beta.5 do not check signatures; they still read `latest.yml`/`beta.yml`, which
  releases keep carrying for them.

## Access to GitHub

- **Own GitHub App.** RunClub signs in through its GitHub App “RunClub” (device flow) and acts on the user's behalf,
  but only in repositories the app is installed on. It requests: Administration (read and write: just-in-time runner
  registration, removing runners, the fork pull request setting), Actions (read and write: runs, jobs, re-runs),
  Variables (read and write: `CI_RUNNER`), Checks (read), Contents (read: workflow files and RunClub's own releases),
  Metadata (read), and for the account Plan (read: billing for the minutes quota). It cannot change code directly, but
  Administration (write) reaches further: with it, a stolen token could change repository settings, collaborators and
  visibility, and through a new collaborator also code. RunClub itself uses it only for runners and the fork setting.
- **Token storage.** The user access token expires after eight hours and is renewed with its refresh token, which
  GitHub accepts only once; the new pair is written before it is used. If Windows holds the file and the rename
  fails, the new pair stays next to it (`github.token.new`) and wins at the next start; the log says so. Both are stored in RunClub's data folder
  (`github.token`), encrypted with Electron's `safeStorage` (DPAPI, bound to the Windows user). Without `safeStorage`
  (the backend alone) the token lives in memory only. The token is never written to the log, and the one-time code
  only appears in the window.
- **Signing out** forgets the token on this computer and deletes both files; if that fails, the log says so. Revoking it on GitHub needs the app's client secret, which
  RunClub does not ship; the window links to GitHub's “Authorized GitHub Apps” page for that. The token is only
  ever sent to `api.github.com` (and `github.com` for signing in); the updater drops it when a download redirects
  elsewhere.

## Accepted on purpose

- **Jobs have full outbound network access**, including your local network (router, NAS, printers) and anything
  Windows can reach, such as a VPN. Their networks are ordinary Docker bridges without an egress filter.
- **Jobs can reach services on Windows' localhost** through `host.docker.internal`. Blocking it would break jobs that
  need a local service. RunClub warns if Docker exposes its own daemon there without protection.
- **Caches are shared across branches** of a repository: the package cache and the build layers. Any job of a
  repository can write to them, clear them, and probably read earlier builds of the same repository. Other
  repositories are not reachable.
- **The runner's registration is readable by the job's steps** (through `/proc` of the runner, same user). It is valid
  for that single job only and does not appear in `env`, `ps` or `docker inspect`.
- **`--network host` in a job container** sees the network of the job's Docker daemon, not that of the runner. Services
  a step starts on the runner's `localhost` are not visible there, and vice versa. Published ports (`-p`, `services:`)
  work as usual.
- **AppArmor** is not active in Docker Desktop's VM. The daemons are started with `apparmor=unconfined` so they also work
  where Docker runs on a kernel with AppArmor, whose default profile would forbid their mounts.
- **`systempaths=unconfined`** for the daemons: rootless Docker and BuildKit mount their own `/proc`, which Docker's
  masked paths would prevent. It makes paths like `/proc/timer_list` and `/proc/keys` readable inside the daemon's
  container; the daemon runs as an unprivileged user, so it cannot write to `/proc/sys` or `/sys`.
